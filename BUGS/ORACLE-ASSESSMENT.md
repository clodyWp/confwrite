# Oracle 独立评估：挑战三轮审查的结论

**评估时间**: 2026-01-09  
**评估者**: Oracle（独立第二意见）

---

## Oracle 的 5 个核心挑战

### 挑战 1：根因分析不完整 ❌

**问题**：我们推断"wordBudget 运行时为 undefined"，但**没有直接证据**。

**已有的间接证据**：
- Task 文件中第 7 节不存在 ✅
- 代码显示第 7 节只在 wordBudget 为 truthy 时生成 ✅
- State 当前有 wordBudget ✅

**缺失的直接证据**：
- ❌ 没有日志显示 18:37 时 state 的状态
- ❌ 没有解释为什么 wordBudget 会为 undefined（outline 在 17:54 就生成了）
- ❌ 没有排除其他可能性

**Oracle 提出的替代解释**：
1. **Phase 2 副作用**：Phase 2 修改 `currentPhase='3'`，与 waitPoint 机制冲突，导致 state 不一致
2. **状态机竞态**：状态机加载 state → 执行 Phase 2 → 保存 state，但 Phase 2 内部也保存 state，可能导致内存 state 覆盖磁盘 state
3. **Phase 3 未执行**：Phase 3 调用 `organizeMaterials` 同步 chapters 到 state，如果跳过则 wordBudget 可能未同步

**结论**：根因分析基于**未经证实的假设**。

---

### 挑战 2：修复方案过度设计 ❌

**我们的方案**：
- 新增 `src/config/word-budget.ts` 共享模块
- 统一 MIN_CHAPTER_CHARS
- 修改 5+ 文件
- 预计 4-6 小时

**Oracle 的简化方案**：

**一行修复**：
```typescript
// 在 generateReviewerPrompt 方法签名中添加默认值
wordBudget: { min: number; max: number } = { min: 5000, max: 8000 }
```

**两行修复**：
```typescript
// 1. 添加默认值（同上）
// 2. 删除第 3 节的字数检查，改为引用第 7 节
```

**为什么更简单更好**：
- 修复了直接问题（第 7 节缺失）
- 不引入新抽象
- 风险更低
- 30 分钟完成，而不是 4-6 小时

**Oracle 的判断**：共享 `word-budget.ts` 模块是**过早优化**。

---

### 挑战 3：执行顺序可能错误 ❌

**我们的顺序**：先修字数配置 → 再修状态机

**Oracle 的质疑**：
> 如果状态机才是真正的问题，修字数配置不会有帮助。

**证据**：
- Phase 2 有已知副作用：修改 `currentPhase='3'`，与 waitPoint 冲突
- 这可能导致 state 不一致
- 如果 state 不一致，wordBudget 可能无法正确传播

**Oracle 建议的顺序**：
1. 先修 Phase 2 状态机问题（移除副作用）
2. 再修字数配置
3. 测试

---

### 挑战 4：可能存在群体思维 ⚠️

**现象**：三个 reviewer 都同意对抗性审查"方向正确但有遗漏"。

**群体思维的信号**：
- 所有 reviewer 聚焦相同方面（代码正确性、完整性、可行性）
- 没有人挑战基本假设（"wordBudget 真的为 undefined 吗？"）
- 没有人提出根本不同的解决方案

**一个持不同意见的 reviewer 可能会说**：
- "我们没有足够证据证明 wordBudget 为 undefined，需要加日志验证"
- "修复方案过度设计了，应该从简单修复开始"
- "状态机问题可能是真正的根因，应该先修"

---

### 挑战 5：遗漏了更深层的设计问题 ❌

**我们发现的 9 个 bug 都是表面问题**。可能存在的深层问题：

**问题 1：字数预算设计**
- 预算 5000-8000 字/章
- 实际写了 15000+ 字
- 预算本身是否合理？是否太严格？
- 如果 Writer 总是超标，也许预算需要调整

**问题 2：Reviewer 职责不清**
- Reviewer 应该检查字数
- 但 prompt 中有矛盾指令（第 3 节 vs 第 7 节）
- 说明职责分离不清晰

**问题 3：状态机复杂度**
- 多个 phase，每个有自己的逻辑
- Phase 2 有副作用与 waitPoint 冲突
- 说明状态机太复杂，需要重构

**问题 4：缺乏可观测性**
- 没有足够日志来调试这类问题
- 只能从间接证据推断根因
- 说明需要更好的可观测性（日志、指标、追踪）

---

## Oracle 的 5 个建议

### 1. 先收集更多证据，不要急着修

**具体做法**：
- 在 dispatcher 中加日志，记录读取 wordBudget 时的值
- 在 generateReviewerPrompt 中加日志，记录 wordBudget 是否为 truthy
- 重新执行 E2E 测试，检查日志
- 获得**确定性证据**

### 2. 从简单修复开始

**具体做法**：
- 给 wordBudget 参数添加默认值（一行）
- 删除第 3 节的字数检查（一行）
- 测试看是否有效
- 如果有效，完成。如果无效，再做更复杂的修复

### 3. 先修状态机

**具体做法**：
- 移除 Phase 2 的副作用（`currentPhase='3'`）
- 确保状态机正确处理 waitPoint
- 测试 state 是否一致
- 然后根据需要修字数配置

### 4. 改进可观测性

**具体做法**：
- 在系统中添加全面的日志
- 添加指标追踪字数、审阅 verdict 等
- 添加追踪，跟随从 init 到 done 的流程
- 使未来调试更容易

### 5. 重新考虑字数预算设计

**具体做法**：
- 质疑 5000-8000 的预算是否合理
- 如果 Writer 总是超标，也许太严格
- 考虑更灵活的预算（如软限制+惩罚）
- 或者完全移除预算，让 Writer 自行决定

## 我的评估

Oracle 的挑战**非常有价值**，特别是：

1. **根因未证实**：我们确实没有直接证据证明 wordBudget 为 undefined。Oracle 提出的替代解释（Phase 2 副作用、状态机竞态、Phase 3 未执行）都是合理的。

2. **修复方案过度设计**：新增共享模块确实是过早优化。两行修复足以解决直接问题。

3. **执行顺序可能有误**：先修状态机确实更合理，因为状态不一致可能是根因。

4. **群体思维风险**：三个 reviewer 确实都没有挑战基本假设。

5. **深层问题**：字数预算设计、可观测性不足等问题确实被忽略了。

## 结论

Oracle 的独立评估揭示了三轮审查的盲点：
1. 根因基于未证实的假设
