## 问题描述

E2E 测试 v22 中发现 LLM 子代理在写作/修复/审阅过程中不遵守字数约束。

## 现象

### Writer 产出严重超标

| 章节 | 预算上限 | 实际字数 | 超标比例 |
|------|----------|----------|----------|
| ch001 | 7800 | 10999 | 141% |
| ch002 | 7800 | 9260 | 119% |
| ch003 | 7800 | 11510 | 148% |
| ch004 | 7800 | 13653 | 175% |
| ch005 | 7800 | 11351 | 146% |
| ch006 | 7800 | 11325 | 145% |

### Fixer 修复后反而增加字数

| 章节 | v1 (Writer) | v2 (Fixer) | 变化 |
|------|-------------|------------|------|
| ch001 | 10999 | 12459 | +1460 |
| ch003 | 26362 | 30348 | +3986 |

Fixer 本应精简内容，但实际上增加了字数。

### Reviewer verdict 矛盾

Reviewer 输出 verdict=accept，但审阅报告 issues 中提到了字数超标问题。验证机制正确拦截了这个矛盾，但说明 Reviewer LLM 的判断不一致。

## 根因分析

DIAG 日志确认 wordBudget 已正确传递到 prompt（min=5200, max=7800）。

问题在于 LLM 收到字数约束后仍然产出了超长内容。这是 **Prompt 工程问题**，不是代码 bug。

可能原因：
1. Writer prompt 中字数约束不够强硬
2. Fixer prompt 没有明确要求「精简」而非「重写」
3. Reviewer prompt 中字数检查指令与 verdict 判断逻辑不一致

## 验收标准

- [ ] Writer prompt 强化字数约束（如分段限制、硬性截断指令）
- [ ] Fixer prompt 明确要求精简到预算范围内
- [ ] Reviewer prompt 统一 verdict 判断逻辑
- [ ] E2E 测试 Writer 产出在预算范围内（允许 10% 容差）
- [ ] E2E 测试 Fixer 产出比 v1 更短

## 优先级

P0 — 直接导致无限循环（配合 #41），浪费大量 token
