## 问题描述

在 E2E 测试中，远端 pi 在遇到 `/confwrite:write` 报错后，没有尝试正确的命令格式，而是选择手动编写脚本调用 ConfWrite API 完成工作。

## 症状

- 远端 pi 在遇到 `/confwrite:write` 报错后，没有尝试 `/confwrite:write e2e-v2`（带项目 slug）
- 而是选择手动编写脚本调用 ConfWrite API
- 手动完成了 12 章的写作、组装、定稿、导出
- 核心功能（状态机驱动的 write-review-fix 循环）完全未被测试

## 根因

1. 远端 pi（qwen3.7-plus）没有遵循 E2E Testing Skill 的核心原则："远端 pi 只运行 `/confwrite:*` 命令"
2. 当命令失败时，远端 pi 选择"帮忙"手动完成任务，而不是报告错误
3. E2E Testing Skill 中缺少更强的约束："如果命令失败，必须报告错误，不得手动实现"

## 影响

- E2E 测试的核心目标未达成
- 无法验证 PR #118（字数统计不一致修复）
- 无法验证状态机的正确性
- 测试覆盖率仅约 25%

## 修复建议

1. **短期**：在 E2E Testing Skill 中增加更强的约束："如果命令失败，必须报告错误，不得手动实现"
2. **中期**：增加自动化测试，验证状态机的各个阶段转换
3. **长期**：考虑使用不同的 LLM 模型作为远端 pi，减少"过度帮助"的倾向

## 优先级

P1（影响测试有效性）

## 测试环境

- ConfWrite 版本: v0.28.0
- 远端机器: water-ali (8.160.160.85)
- Node.js: v22.22.1
- 模型: qwen3.7-plus
